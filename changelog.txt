== Changelog ==

Every change to SEO Pro Stack. readme.txt lists the latest version in short.

= Unreleased =
* New: Correct update counts (Admin tab, on by default). The numbers next to Dashboard › Updates, Plugins and Appearance no longer count updates already installed by the host, a deploy or a file upload, which WordPress keeps counting for up to 12 hours while the Updates screen lists none. Only the numbers change.
* Fix: with Load plugins only where needed, a wp-admin screen where WordPress's twice-daily update check is due loads every plugin, at most once an hour, so updates that plugins such as Kadence Blocks and SliceWP add are in the check. Screens that skip those plugins still count their updates.
* Changed: Load plugins only where needed shows only its switch and status. Its other settings, bypasses for a plugin or theme it does not handle, are in a closed Troubleshooting section of its Options, which opens by itself when one of them is changed or a page of the site failed with fewer plugins. Each says which problem it fixes. Values and defaults are unchanged.
* Fix: Hosting needs no longer asks for more PHP workers and CPU cores than a site needs. Workers come from the average time per request, not the time 95% of pages took (rounded up to its timing slot), which counted slow requests twice on top of the busiest hour and its bursts. Now uses the average of every request, admin screens and cron included, as its busiest hour counts them all; the traffic levels use visitors' pages. On one measured site, Now went from 7 workers and 8 CPU cores to 4 and 4. The traffic line shows both averages and the 95% page time.
* Fix: Hosting needs no longer warns that LiteSpeed Cache's object cache "did not keep a test value between daily checks" while it works. Its Purge All, on every plugin update by default, empties the object cache, so the test value was lost. LiteSpeed Cache's cache is now checked only by asking its server, which shows whether it falls back to the database; other object caches still keep a test value. The warning clears on the next admin screen.
* New: Hosting needs says how PHP runs (PHP-FPM, LiteSpeed, FastCGI, Apache's mod_php or CGI) in Site Health Info, and advises asking the host for PHP-FPM or LiteSpeed when PHP runs inside Apache or starts afresh for every request. Its PHP worker lines name the server's setting for them, such as pm.max_children, so they can be sent to a host as they are.
* New: a Directory listing test in Site Health. Once a day it checks whether anyone can list the files in the uploads folder, and if so, what to ask the host for. Nothing is written to server files.
* Fix: Hosting needs no longer says an object cache is available but not used for up to a day after it is turned on (for example in LiteSpeed Cache → Cache → Object, or with the host's object cache switch), nor that one works after it is turned off. When WordPress starts or stops using an object cache, it is checked again on the next admin screen.

= 1.3.7 =
* Fix: with Load plugins only where needed, more options that plugins save again on wp-admin page views no longer make the site's pages learn again: MainWP Child's HTML Regression asset list, StellarWP Uplink's update status for Kadence and StellarWP products, Burst Statistics' detected integrations, and Really Simple Security's notice cache and menu badge count.
* Fix: with Load plugins only where needed, anything a plugin saves while a wp-admin screen is only viewed, and opening the post editor, no longer makes the site's pages learn again, whichever plugin it is. Sent forms, links that change something, AJAX, the REST API, WP-CLI and content, plugin and theme changes still do.
* Changed: Load plugins only where needed replaces Freesoul Deactivate Plugins and its PRO add-on. The Plugins screen suggests removing them, and the feature waits while either is active. Freesoul's hand-made lists are not imported: only plugins learned as not needed are skipped.

= 1.3.6 =
* Fix: Magic login links keeps HandyPlugins' Magic Login blocks working in pages and synced patterns after the plugin is removed. Saved text, safe redirects and logged-in visibility are preserved. With the feature off, WordPress's password form keeps login available; page learning recognises the block.
* Fix: with Load plugins only where needed, a shortcode or block that a plugin registers only on some posts is no longer taken for a leftover from an old theme or removed plugin: the active plugins' code is searched first, so that plugin keeps loading on the posts using it.
* Developers: STANDARDS.md from WP Plugin Starter 1.0.22. Performance has a new rule, Small choice lists: a select or multi setting's options callable runs on every settings save, so it must never list what grows with the site (the cause of the settings-save memory fix in 1.3.0).

= 1.3.5 =
* Fix: with Load plugins only where needed, a page with shortcodes or blocks that no plugin registers (left by an old theme or a removed plugin) in its own content learns once and then skips plugins, instead of loading every plugin on every visit.

= 1.3.4 =
* Fix: with Load plugins only where needed, shortcodes and blocks left by a removed plugin, in a widget or in posts listed on archives, no longer make pages load every plugin.
* Fix: Load plugins only where needed learns and skips plugins on items served at short addresses (Short addresses for custom post types), which used only the site-wide choices. Readabler's cron timestamp no longer makes pages learn again.

= 1.3.3 =
* Fix: FluentCRM's background tasks no longer make the site's pages learn again: all eight of its run timestamps are known as records, not only two.
* Fix: failed logins no longer make the site's pages learn again. Login limiters such as Really Simple Security save each failed attempt as an option, and bots try to log in all day, so on some sites pages never stayed learned.

= 1.3.2 =
* Fix: Load plugins only where needed kept what an older SEO Pro Stack had learned about the site's pages and admin screens when SEO Pro Stack was updated without WordPress's updater (WP-CLI with --skip-plugins, a deploy, an upload or a Git pull), so a fix to page learning did not reach those sites until their content changed. A new SEO Pro Stack version now learns again on its first request, however it was installed, and the settings list it among the changes that made pages learn again. New `seoprostack_plugin_learned_by` option, removed on uninstall.
* Fix: Load plugins only where needed still made the site's pages learn again every few minutes on sites with MainWP Child, Really Simple Security, FluentCRM or Readabler: their background tasks save more records than 1.2.0 knew (system monitor runs, request IDs, header test expiry, sequence runs, process timestamps). Those records are now known by their name's start, so the site's pages stay learned.

= 1.3.1 =
* Fix: on sites with a persistent object cache (LiteSpeed, Redis, Memcached), Load plugins only where needed could stop learning the site's pages after they were reset, so every page loaded every plugin until the cache dropped an old copy of what was learned. WordPress removes a deleted option only from its list of options loaded on every request, so a second cached copy stayed and the next save was lost. SEO Pro Stack now removes both, and saves over an old copy on sites that are stuck.

= 1.3.0 =
* New, on by default: Recommended speed settings (Speed tab). A plan below the Speed tab's settings, from the site's own size and plugins: which speed and server settings to turn on, why for this site and what each costs, and why the others are not recommended here. Turn on changes one setting as its switch would; Undo puts it back while it is still as the plan left it. Changes nothing until someone clicks. New `admin_post_seoprostack_speed_plan` action and `seoprostack_speed_plan` log option (not autoloaded), removed on uninstall.
* Fix: saving a setting ran out of memory on sites with tens of thousands of pages: every save listed every page for the Client dashboard's hidden page choices. They now keep the page ID without a list.
* New, off by default: Remember admin counts (Server tab). On sites without a persistent object cache, the site's comment counts (as WooCommerce adjusts them), each post type's counts, count_users() and WooCommerce's pending product reviews count are kept between requests instead of counted on every admin screen, and counted again after any change made through WordPress; a count is kept at most an hour. With 500,000 comments and WooCommerce, a settings screen's queries went from 189 ms to 12 ms. New `seoprostack_admin_counts` option (not autoloaded), removed when turned off and on uninstall.
* Fix: a synced pattern that nothing uses no longer stops Load plugins only where needed skipping plugins on the whole site. Page learning read every published synced pattern, so one left over from a removed plugin (such as a Bookly form) made every page load every plugin; synced patterns now count only where a post, template part or widget uses them.

= 1.2.0 =

Tools → Add database keys offers a key on postmeta and on usermeta (single sites) for finding posts and people by a custom field's value, and one on Action Scheduler's tasks. Each is added online (the table stays usable) only when someone clicks, never when an existing key covers the same columns, and removed with Remove or on uninstall. Only keys named sps_ are ever removed; Database key cleanup lists them as SEO Pro Stack's and never offers them. New `wp seoprostack keys list|add|remove` command, `admin_post_seoprostack_add_keys` action and `seoprostack_added_keys` log option (not autoloaded), removed on uninstall.
* New, off by default: Calls to other sites (Server tab). Tools → Calls to other sites lists each plugin's, theme's and must-use plugin's calls through WordPress's HTTP API by host: calls sent and not sent, failures, total, average and slowest time, last answer, where they were made and the last path (no query string). Block stops one plugin's calls to one host; payment services, WordPress.org and WordPress.com, the site itself, WordPress, SEO Pro Stack and WordPress's update code are never blocked. New `seoprostack_outbound_never_block` filter, `admin_post_seoprostack_outbound_calls` action and the `seoprostack_outbound_calls` and `seoprostack_outbound_blocks` options (not autoloaded), removed on uninstall.
* Fix: Load plugins only where needed with page learning still made the site's pages learn again every minute or two on sites with LiteSpeed Cache, FluentCRM, Really Simple Security or MainWP Child, whose background tasks save records through AJAX. AJAX and REST requests with nobody signed in now only keep records, as cron and page views do, and those plugins' record options are known.
* Fix: two settings saves at the same moment can no longer both take over a stale save lock, so one no longer overwrites the other. A save keeps the settings of features not loaded on that request. Text settings sent as a list are refused instead of saved as "Array", and an address with a backslash is refused. From WP Plugin Starter 1.0.21.
* Fix: Updates from GitHub (shared updater 1.1.1) finds the release zip whatever the case of the repository name, and reports a renamed or moved repository instead of finding no release.
* Developers: core files from WP Plugin Starter 1.0.21. The smoke, update and Plugin Check scripts fail when they cannot check and remove every container; .wporg-links replaces whole links only, also in SVG, XML and translation files; the preflight finds referral links written with &amp; and scans Markdown, CSS, SVG, XML and translation files; rename-plugin.sh and sync-core.sh stop on failed writes, and sync-core.sh refuses symbolic links and compares the executable bit.
